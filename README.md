# 一、十分钟跑起来（团队伙伴从这里开始）

## 0. 你会收到什么

队长会用**两种方式之一**发给你，先确认自己是哪一种：

### 方式 A · 收到一个 zip（「开箱即用包」，推荐）

解压后**代码、知识库、已发布规则库、样例语料全都在里面**。你只需要：

```
解压 → 第 3 步 建虚拟环境装依赖 → 第 4 步 配 API Key → 第 5 步 启动 → 第 6 步 登录
```

**第 2 步（下载代码）和第 7 步（导入材料库）都不用做** —— 代码就在包里，知识库也已预建好
（42 份文档 / 99 个检索片段），启动后打开页面**直接就能问、直接就能审材料**。

### 方式 B · 只收到一个 GitHub 链接

| 东西 | 怎么拿到 | 干什么用 | 最后放到哪 |
|---|---|---|---|
| **① 代码** | 队长发的 GitHub 链接 | 程序本体 | 第 2 步下载到本地 |
| **② API Key** | **队长私下单独发** | 调用大模型 | 填进 `.env`（第 4 步） |
| **③ 材料库压缩包** | **队长私下单独发** | 知识库语料 | 解压后上传进系统（第 7 步） |

### 无论哪种方式

**API Key 都必须由队长私下单独发给你** —— 它不在 GitHub 上，也不在 zip 包里。

## 3. 创建虚拟环境并装依赖

> 为什么要虚拟环境：把这些依赖装进项目自己的小盒子里，不污染你电脑上的 Python。

**Windows（在项目目录里打开 cmd 或 PowerShell）**

```bash
python -m venv .venv
.venv\Scripts\activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

**macOS / Linux**

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

**两个加速提示**（可选）

- 不需要 GPU 时，先装精简版 torch 再装其余依赖，能省下好几个 G：
  ```bash
  pip install torch --index-url https://download.pytorch.org/whl/cpu
  ```
- pip 下载慢就加国内源：
  ```bash
  pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple
  ```

装的过程要几分钟（torch 比较大），耐心等。**看到激活成功时命令行前面会有 `(.venv)` 前缀**，后面所有命令都要在这个状态下执行。

## 4. 配置 API Key（★ 关键一步）

### 4.1 把模板复制成正式配置文件

```bash
copy .env.example .env          # Windows cmd
Copy-Item .env.example .env     # Windows PowerShell
cp .env.example .env            # macOS / Linux
```

### 4.2 用记事本打开 `.env`，填两个值

找到最上面这两行：

```ini
ARK_API_KEY=
ARK_MODEL=
```

改成（**把 `ARK_API_KEY` 换成队长私下发给你的那串字符**）：

```ini
ARK_API_KEY=这里粘贴队长给你的那串字符
ARK_MODEL=
```

### 4.3 关于 `ARK_MODEL` 要不要填

**结论：留空就行。**

原因：方舟的「API Key」和「推理接入点 ID」是**绑定同一个账号**的一对——
用谁的 Key，就得配谁的接入点。队长给你的 Key 是他账号的，
而他的接入点 ID 已经作为默认值写在 `config.py` 里（`ep-20260919155615-h2mfv`），
所以**留空即会自动匹配上**。

> 例外：如果队长在发 Key 的同时还单独发了「接入点 ID」，
> 那就以他发的为准，填到 `ARK_MODEL=` 后面。

### 4.4 验证有没有读进去

在项目目录、虚拟环境已激活的状态下执行：

```bash
python -c "import config; print('API Key 已读到:', bool(config.ARK_API_KEY)); print('接入点:', config.ARK_MODEL)"
```

期望输出 `API Key 已读到: True`。如果是 `False`，说明 `.env` 没放在项目根目录，或者文件名叫成了 `.env.txt`（Windows 记事本容易犯这个错）。

### 4.5 ⚠️ 三条铁律

1. **`.env` 绝不提交到 git。** 它已经在 `.gitignore` 里，不要用 `git add -f .env` 强行加进去。
2. **不要把 Key 发到任何群里**，也不要贴进 issue、聊天记录、截图里。
3. **不要把 `.env` 打进任何要发给别人的压缩包**（包括你想分享给其他同学时）。

> 这个 Key 消耗的是**队长的额度**，泄露出去别人也能用。请当密码对待。

## 7. 导入材料库（把语料喂给系统）

> **用「开箱即用包」的话跳过本节** —— 知识库已经预建好了（42 份文档 / 99 个检索片段），
> 打开页面直接就能问、直接就能审材料。只有想**自己重走一遍上传流程**时才需要往下看
> （包内 `样例语料（原始文件）/` 就是本节要用的材料，结构与下面 7.1 完全一致）。

### 7.1 材料库长什么样

解压队长给你的压缩包，会得到：

```
材料库/
├── 01_公开通知/          39 份面向全校公开的通知、公告、活动预告
├── 02_制度规则/          综合素质测评实施细则（材料审查的规则来源）
├── 03_待审材料/          虚构的学生材料「张三」（用来试审查）
└── README_样例包说明.txt
```

> `03_待审材料/` 里的人物是**纯编造的**，请勿替换成任何真实学生材料。

### 7.2 方式一：在网页上逐份上传（适合少量文件）

用 `reviewer` 或 `admin` 登录 → 左侧导航进「**文档管理**」→ 选择文件 → 上传。
传完左边的知识库条目数会增加。

### 7.3 方式二：命令行批量上传（适合整个材料库）

**先把服务启动起来**（第 5 步那个窗口别关），再**另开一个命令行窗口**，
进入项目目录、激活虚拟环境，然后：

```bash
python tools/batch_upload.py "解压后的材料库目录" --recursive
```

举个具体例子（路径换成你自己的）：

```bash
python tools/batch_upload.py "D:/材料库" --recursive
```

几个有用的开关：

| 参数 | 作用 |
|---|---|
| `--dry-run` | 只列出「将会上传哪些文件」，不真的上传（建议先跑一次） |
| `--report upload_report.json` | 把每个文件的成败详情写成 JSON |
| `--base-url http://127.0.0.1:8002` | 服务不在默认 8001 端口时指定地址 |
| `--stop-on-error` | 遇到第一个失败就停 |

脚本默认使用 `reviewer / Demo@123456` 登录，需要换账号时加 `--username`、`--password`。
完整参数见 `python tools/batch_upload.py --help`。

传完可以打开「知识库」页面确认条数。

# 二、两条链路怎么用

## A. 制度问答（简单，传完就能用）

左侧进「**智能问答**」，直接提问，例如：

- 四六级什么时候报名？
- 计算机等级考试怎么报？
- 台风天学校有什么提醒？

你会看到：

- **回答是逐字打出来的**（流式输出），不是等半天才一次性出现；
- 回答下方有「**参考来源**」，点标题可以打开原文；
- 知识库里确实没有的问题，它会明确说「根据现有资料，我无法准确回答」——
  **这是设计如此**，目的是不编造答案。想让它答得出来，就先把对应文件传进知识库。

## B. 材料审查（开箱即用，直接传材料就出报告）

材料审查靠的是「**规则**」。规则不是手写的，是系统从**制度文件**里自动抽出来、再由人工审核发布
—— 但**已发布的那一份（`auto_rules.json`）随代码一起分发**（它是被 git 跟踪的正式配置，
不是运行时数据）。所以：

> **不需要任何前置操作，直接上传待审材料就能出报告。**
>
> 实测：上传 `03_待审材料/张三_综测佐证材料（虚构）.docx` → 识别为「**综合素质测评**」，
> 套用 **30 条**规则，结论「**待核验**」（总评分 93 / 硬规则 100 / 软审查 83），约 **7 秒**出结果。

自带的正式规则库覆盖 **6 个领域 / 165 条规则**：
综合素质测评 40、考试报名管理 30、四六级考试报名、学科竞赛管理、校园艺术活动、团员推优。

### 上传材料出报告

用任意账号登录 →「**材料预审**」（或聊天页左下角的附件按钮 ⌕）→ 上传
`03_待审材料/张三_综测佐证材料（虚构）.docx`。

审查过程是**实时滚动**的（SSE 推送后台真实进度，不是演出来的动画），你会依次看到：

```
✓ 材料解析完成          →  已读取 1842 个字符
✓ 识别为综合素质测评 · 综合素质测评
✓ 匹配审查规则          →  已匹配 30 条审查规则
✓ 提取关键事实          →  已整理 33 个关键字段
✓ 分析材料质量
✓ 执行硬规则            →  3 条通过，21 条待核验
✓ 生成审查报告
```

报告里会给出**审查结论**（通过 / 需修改 / 待核验 / 未通过 / 无法审查）、
**综合评分**、逐条规则的**校验明细**和**制度依据**（可点开原文）。

### 什么时候才需要「上传制度 → 审核 → 发布」这三步

**只有想给系统加新规则时才需要**（上面那次实测就完全没做这三步）：

- **换一所学校**：`domains/*.yaml` 和 `auto_rules.json` 里都是本校的领域与规则；
- 你手上另有**新的制度文件**，希望系统按它来审材料。

这时才走：

1. **上传制度文件**：用 `reviewer` / `admin` 登录 →「文档管理」上传（如 `02_制度规则/` 的综测细则）。
   制度类文件上传后**不会立刻生效**，只会变成一批「候选规则草稿」——这是有意的安全设计。
2. **审核并发布**：点右上角 **🧩** 打开「规则中心」→ 逐条「通过 / 保存修改 / 驳回」→
   最后点「**发布已通过规则**」。
3. 发布之后，新规则才参与审查。

> `rule_drafts.json`（候选草稿）**是被 `.gitignore` 忽略的运行时数据**，仓库里没有；
> 开箱即用包里带了 **16 批 / 229 条**用样例语料预生成的待审草稿
> （其中来自细则的「综合素质测评」20 条质量最好，通知类文档抽出的那 14 批可以先忽略）。
> **不处理它们也不影响上面的审查** —— 它们只是待你决定要不要并进正式规则库。

### 附：学生提交 → 审核员处理

`student` 预审完可以点「提交正式审核」；`reviewer` / `admin` 在「材料审核」里
能看到队列，把状态标成**审核中 / 需修改 / 已通过**并填写人工意见。

# 三、常见问题

| 现象 | 原因与解决 |
|---|---|
| `ModuleNotFoundError: No module named 'fitz'`（或 `rapidocr_onnxruntime` / `docx2txt` / `multipart`） | 依赖没装全。确认虚拟环境已激活，重跑 `python -m pip install -r requirements.txt` |
| 启动时报 `Address already in use` | 8001 端口被占用，换一个：`python -m uvicorn main:app --port 8002` |
| 首次启动卡在下载模型 / 报 502 | 网络问题。项目已默认把 HuggingFace 指向 `hf-mirror.com`；若你开了系统代理，试着临时关掉 |
| 问答回答「网络请求超时或服务暂时不可用」 | Key 不对、额度用尽或网络不通。先跑 [4.4 的验证命令](#44-验证有没有读进去) |
| 登录后立刻又跳回登录页 | 请确认访问的地址就是 `http://127.0.0.1:8001/`，不要用 IP 或别的端口 |
| 提示「规则库未初始化，请先上传规章制度文件」 | `auto_rules.json` 被删了。它正常随代码分发，从仓库/压缩包里恢复该文件即可 |
| 审查结果说「无法审查」 | 材料类型没匹配到任何**已发布**规则。做法：传对应制度文件 → 🧩 规则中心审核发布 → 再审查（见 [二·B](#b-材料审查开箱即用直接传材料就出报告)） |
| 审查长时间停在「提取关键事实」 | **这一阶段最慢，正常约 10~35 秒**；超过 2 分钟才需要排查 |
| 中文文件名在 mac/Linux 上解压乱码 | 是 Windows 自带压缩的问题，换 7-Zip 打包/解压 |
| 想重置一切从零开始 | 停掉服务，删掉 `chroma_db/`（向量库）、`auth.db`（账号）、`rule_drafts.json`，重启即可。⚠️ **别删 `auto_rules.json`** —— 那是已发布的正式规则库，删了材料审查会变成「无法审查」，只能重新上传制度文件、逐条发布来重建 |

# 四、项目概况

## 核心功能

- 🔍 **智能问答**：知识库精准问答 + 多轮对话 + 来源溯源 + 拒答
- 📋 **材料审查**：自动抽取规则 + 场景隔离 + 硬规则校验 + 软性审查（与事实抽取并行）+ 三档扣分
- 🧩 **规则治理**：制度文件只生成候选草稿，负责人逐条通过、编辑或驳回后再统一发布
- 📄 **多格式支持**：PDF / Word（含 .doc）/ TXT / 图片 / 扫描件 OCR ——
  上传与审查两条链路共用同一套解析，不会出现「前端能选、后端解不了」
- ⚡ **查询缓存**：重复问题 0 次模型调用，约 3 毫秒返回
- 👤 **轻量用户体系**：账号登录 + 学生/审核员/管理员权限 + 个人问答与审查历史
- 🧭 **角色工作台**：三种角色登录后进入不同首页与业务导航
- 🔄 **材料流转**：学生预审后提交，审核员可标记审核中、退回修改或审核通过
- 📊 **可观测接口**：`/stats` 实时查看调用次数、缓存命中率、当前生效配置

## 技术栈

| 层 | 用的什么 |
|---|---|
| 后端 | FastAPI + LangChain + Chroma |
| 大模型 | 火山引擎方舟（推理型模型） |
| 嵌入 | BAAI/bge-small-zh-v1.5 |
| 精排 | BAAI/bge-reranker-base |
| OCR | RapidOCR + PyMuPDF |
| 配置与提示词 | `config.py` / `prompts.py` / `domains/*.yaml` |
| 测试 | pytest（纯逻辑用例不加载模型，秒级可跑） |

## 相对原版的三个改动

1. **校规不再写死在代码里** —— 文档白名单、场景互斥、专有名词等学校特有约束
   全部移到 `domains/*.yaml`。换一所学校只改一份配置，代码不动。
2. **模型调用收口** —— 原来接入点 ID 硬编码 10 处，现在只在 `config.py` 出现 1 次；
   所有调用经过统一出口，自动计数、统一超时与温度。
3. **调用次数降 40%，上界确定** —— 相关性判定由「每条资料一次请求」合并为
   「一次批量判定」；关闭 SDK 自动重试，消除「4 秒超时实际等 12 秒」的问题。
   调用次数由 `tools/llm_proxy.py` 出站计量代理**实测**（两版口径一致），
   不依赖改造版独有的 `/stats` 接口推断。

改动内容与实测数据详见 [`改动说明.md`](改动说明.md)。

# 七、规则治理与批量上传

## 批量上传知识库文件

先启动服务，再将整个目录中的支持文件依次上传：

```bash
python tools/batch_upload.py data --recursive --report batch_upload_report.json
```

也可以指定多个文件或目录：

```bash
python tools/batch_upload.py "资料/通知.pdf" "资料/制度目录" --recursive
```

脚本支持 PDF、TXT、DOCX、DOC、PNG、JPG/JPEG，默认连接 `http://127.0.0.1:8001`。
上传前想先确认文件清单可加 `--dry-run`；服务在别的地址用 `--base-url http://主机:端口`。
服务端会跳过内容完全相同的文件，同名但内容有变化的文件会作为新版本入库。

## 规则审核流程

制度类文件上传完成后**不会立即影响材料审查**。点击页面右上角的 **🧩**：

1. 查看模型抽取的候选规则、制度原文与自动预检结果；
2. 逐条选择「通过 / 保存修改」或「驳回」；
3. 所有候选都处理完后，点击「发布已通过规则」。

缺少原文依据、状态规则缺少正反值、字段结构不完整或与正式库重复的规则不能通过。
审核人、操作时间、备注和发布结果保存在 `rule_drafts.json`；
正式审查仍只读取 `auto_rules.json` 中**已经发布**的规则。

# 十一、已知边界

详见 [`改动说明.md`](改动说明.md) 第七、八节。摘要：

- `main.py` 仍是单文件（1717 行）。审查规则引擎已拆到 `review_engine.py`，
  其余部分（文档解析、检索、路由）尚未拆分
- BM25 索引全量重建期间，并发问答可能读到中间状态。当前百级片段影响可忽略，
  上万片段需改增量索引或加读写锁
- 端到端耗时受远程模型波动主导（1.25s～11.5s），未取得稳定优势，
  结论以「调用次数」与「本地检索耗时」这两个确定性指标为准
- `/review` 已改用独立 `TIMEOUT_REVIEW`（默认 60s），事实抽取与软审查并行发起；
  结构化阶段默认关闭深度思考并要求 JSON 输出，软审查还会校验完整字段和数值评分，
  不会再把「可解析但缺评分」的字典误报为成功
- 审查依据会把规则库原文件名关联到 `data/` 中的实际归档版本，前端可直接点击预览；
  没有归档原文的旧规则会明确显示「原文未归档」
- `domains/gdut.yaml` 与规则库 `auto_rules.json` 的领域错配**已修复**：
  4 个「有规则却未声明」的领域（共 96 条）已写进 yaml；6 个「零规则且无兜底」的领域
  （请假管理/学生干部/违纪处分/转专业申请/宿舍管理/助学贷款）已从 yaml 移除。
  yaml 内写明不变量：只声明「规则库确有规则」或「有 `rule_domain_fallbacks` 兜底」的领域；
  后续上传对应制度文件会自动抽取入库，届时把领域加回清单即可（详见评测报告缺陷 D1）
- **规则数据质量已设防**（缺陷 D11~D13）：规则抽取把制度条文编成规则时，错编语义**不会报错**，
  只会静默把合格材料判成不合格（实测：一份没有挂科的综测材料被判「存在挂科」）。
  现由三层防线兜住 —— 抽取提示词约束 type 的选用规则、引擎的 `status` 三态与元规则判定、
  以及 `tests/test_rule_library_guards.py` 对真实 `auto_rules.json` 的守卫断言
  （该守卫在首次运行时就抓出第三条同类规则）。详见 `改动说明.md` 第 9.4 节
- CRAG **只实现了 Correct 态**，缺 Incorrect（Web 搜索兜底）与 Ambiguous。
  对外表述宜为「参考 CRAG 的判定思路，针对校园场景裁剪」，而非「完整实现了 CRAG」
